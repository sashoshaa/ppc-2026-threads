## Введение

OpenMP-версия предназначена для распараллеливания двух этапов алгоритма:
поразрядной сортировки частей и поуровневого слияния этих частей.

## Постановка задачи

Нужно получить корректную и быструю многопоточную реализацию radix+merge на
основе директив OpenMP, сохранив совместимость с общими тестами задачи.

## Описание реализации

Реализация: `omp/src/ops_omp.cpp`, класс `SosninaATestTaskOMP`.

### Принцип работы

1. Вычисляется число частей:
   `num_parts = min(GetNumThreads(), data.size())`.
2. Каждая часть сортируется `RadixSortLSD` в параллельном цикле:
   `#pragma omp parallel for num_threads(num_parts)`.
3. Отсортированные части сливаются по уровням дерева.
4. Пары на уровне merge также обрабатываются параллельно:
   `#pragma omp parallel for schedule(static)`.
5. Результат проверяется через `std::ranges::is_sorted`.

### Псевдокод

```text
num_parts <- min(GetNumThreads(), |data|)
разбить data на parts

#pragma omp parallel for
for i in [0 .. num_parts):
    LSD-sort(parts[i])

current <- parts
while |current| > 1:
    #pragma omp parallel for
    for idx in [0 .. |current|/2):
        next[idx] <- merge(current[2*idx], current[2*idx+1])
    перенос хвоста при нечётном количестве частей
    current <- next
data <- current[0]
```

## Оценка сложности

- Асимптотика по данным близка к SEQ (линейные radix-проходы + merge).
- Практическое ускорение ограничивается синхронизацией потоков и памятью.

Метрики приведены относительно SEQ: `S = T_seq / T_omp`, `Eff = S / N`.

## Анализ

- Для `N = 2` эффективность близка к линейной.
- При `N = 4` достигается хороший компромисс ускорения/эффективности.
- При `N = 8` ускорение растет, но эффективность падает из-за merge-этапов и
  ограничений подсистемы памяти.
