## Введение

OpenMP позволяет распараллелить **две независимые фазы** алгоритма: независимую поразрядную сортировку частей массива и **поуровневое** слияние пар соседних отсортированных фрагментов. Директивы задают число потоков явно (`num_threads`), что упрощает согласование с переменной окружения `PPC_NUM_THREADS` в инфраструктуре курса.

В отличие от реализаций STL/TBB/ALL, в данной ветке **нет** дополнительных порогов «минимального размера части»: число частей определяется только запрошенным числом потоков и длиной массива (см. код ниже).

## Постановка задачи

Требуется получить корректную многопоточную сортировку того же типа, что и в SEQ (radix LSD + merge), с ускорением на многоядерной машине при сохранении полной совместимости с общими тестами задачи.

## Связь с кодом

## Описание реализации

### Выбор числа частей

После проверки `data.size() > 1`:

```text
num_threads = GetNumThreads()
num_parts   = min(num_threads, static_cast<int>(data.size()))
```

Если `num_parts <= 1`, выполняется однопоточный `RadixSortLSD` по всему массиву (как вырожденный случай).

Иначе вход режется на `num_parts` непрерывных подмассивов с распределением остатка `data.size() % num_parts` по первым индексам частей (как в типичном block decomposition).

### Фаза radix

```cpp
#pragma omp parallel for num_threads(num_parts) default(none) shared(parts, num_parts)
for (int i = 0; i < num_parts; ++i) {
  std::vector<int> buffer(parts[i].size());
  RadixSortLSD(parts[i], buffer);
}
```

Каждая часть сортируется **независимо**; локальный буфер создаётся в теле цикла и не разделяется между итерациями.

### Фаза merge (дерево)

Пока в `current` больше одного вектора:

- вычисляется число пар `current.size() / 2`;
- для каждой пары выделяется `next[i]` нужного размера и вызывается `SimpleMerge`;
- при нечётном числе фрагментов «хвост» переносится на следующий уровень без слияния в этой итерации.

Параллельный цикл по парам:

```cpp
#pragma omp parallel for default(none) shared(current, next) schedule(static)
for (size_t i = 0; i < current.size() / 2; ++i) { ... }
```

`schedule(static)` даёт предсказуемое распределение итераций по потокам при равномерном размере пар (на практике размеры пар на одном уровне могут отличаться — это один из источников дисбаланса нагрузки).

### Проверка результата

После сборки итогового вектора в `data` вызывается `std::ranges::is_sorted(data)`.

### Псевдокод (сводно)

```text
num_parts <- min(GetNumThreads(), |data|)
если num_parts <= 1: одиночный RadixSortLSD(data); конец
разбить data на parts[0..num_parts)

#pragma omp parallel for num_threads(num_parts)
for i: LSD-sort(parts[i])

current <- parts
пока |current| > 1:
    #pragma omp parallel for schedule(static)
    for idx: next[idx] <- merge(current[2*idx], current[2*idx+1])
    учесть нечётный хвост
    current <- next
data <- current[0]
```

## Отличия от STL/TBB

- В OMP **нет** явных констант `kMinElementsPerPart` / `kLargeArrayThreshold`: при большом `GetNumThreads()` и среднем `n` части могут оказаться **мельче**, чем в STL/TBB, что увеличивает число уровней дерева merge и накладные расходы.
- Параллелизм задаётся директивами, а не ручным `std::thread` или задачами TBB.

## Оценка сложности

- Асимптотика по `n` такая же, что у SEQ на полном массиве: **O(n)** radix + **O(n)** суммарно по слияниям на всех уровнях при фиксированной разрядности.
- Практическое ускорение ограничивается **памятью** (пропускная способность к нескольким буферам), **барьерами** между уровнями merge и **дисбалансом** размеров частей/пар.

## Экспериментальные результаты (ориентир)

Окружение при замерах (как в сводном отчёте): Apple M2, macOS, Release, `task_run`, `kCount = 20_000_000`.

Метрики относительно SEQ: `S = T_seq / T_omp`, `Eff = S / N`, где `N = PPC_NUM_THREADS`.

| N потоков | Ускорение S | Эффективность Eff |
| --------- | ----------- | ----------------- |
| 2         | 1,88        | 94%               |
| 4         | 2,58        | 64,5%             |
| 8         | 2,98        | 37,2%             |

Цифры типичные для одной конфигурации машины; при сдаче отчёта рекомендуется **перепрогнать** `ppc_perf_tests` и при необходимости обновить таблицу (см. `report_performance.md` в корне задачи).

## Анализ

- При **N = 2** эффективность близка к «идеальной» линии: мало уровней merge, хорошая загрузка ядер на radix.
- При **N = 4** обычно оптимальный компромисс ускорения и эффективности на 8-ядерном M2.
- При **N = 8** ускорение ещё растёт, но **Eff** падает: узкие места — поздние уровни дерева (мало пар), пропускная способность памяти, конкуренция за кэш.

## Вывод

OpenMP-версия корректна, хорошо интегрируется с моделью курса (`PPC_NUM_THREADS`) и даёт устойчивое ускорение относительно SEQ на рассматриваемой платформе.
