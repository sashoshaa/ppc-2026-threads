## Постановка для сравнения

Для одного и того же размера входа требуется сопоставить:

1. абсолютное время фазы **`Run()`** в режиме `task_run`;
2. ускорение относительно SEQ (`S = T_seq / T_par`) для OMP/TBB/STL и ALL при выбранных `P`, `N`;
3. эффективность использования параллельных ресурсов (см. раздел «Формулы»).

## Методика измерений

- Файл: `tasks/sosnina_a_radix_simple_merge/tests/performance/main.cpp`.

- Для ALL дополнительно: **`PPC_NUM_PROC`**, запуск под **`mpirun -np P`**. Функциональные и часть perf-тестов для `all` требуют MPI.

## Формулы

Пусть **`T_seq`** — время SEQ, **`T_par`** — время параллельной реализации при **`N`** потоках на одной машине (без учёта MPI), **`T_all(P, N)`** — время ALL при **`P`** MPI-процессах и **`N`** потоках на процесс.

- **Ускорение относительно SEQ:** `S = T_seq / T_par` (для ALL подставляем `T_all` при выбранных `P`, `N`).
- **Эффективность для OMP/TBB/STL:** `Eff = S / N` (доля от идеального линейного ускорения в `N` раз).
- **ALL при `P = 1`:** тот же `Eff = S / N`, если сравнение ведётся с SEQ как с однопоточной базой.
- **ALL при `P > 1`:** имеет смысл вводить **общеузловую** эффективность `Eff_global = S / (P * N)`, если трактовать «параллельную единицу» как все потоки всех рангов.

Дополнительно для ALL полезно отдельно считать **масштабирование потоков при фиксированном `P = 1`**: `S_par = T_all(1) / T_all(N)`, `Eff_par = S_par / N` — см. **`all/report_performance.md`**.

## Анализ (расширенный)

1. **TBB** на данном входе чаще всего немного опережает OMP и STL за счёт сочетания `parallel_for`, `simple_partitioner` и порогов зернистости в коде.
2. **OMP** даёт сопоставимое ускорение; при малых массивах может быть выгоднее/хуже TBB в зависимости от числа частей (в OMP-файле задачи нет тех же порогов `kLargeArrayThreshold`, что в TBB/STL).
3. **STL** на `std::thread` переносима и по скорости близка к OMP на `N = 2…4`; на `N = 8` все три технологии упираются в память и в структуру дерева merge.
4. **ALL при `P = 1`** близок к STL по локальной части, но добавляются **`MPI_Scatterv`** и **`MPI_Bcast`**; выгодно сравнивать также `S_par` и `Eff_par` из `all/report_performance.md`.

## Практические рекомендации

- Для **одного узла** с общей памятью в первую очередь рассматривать **TBB** или **OMP**; **`N ≈ 4`** часто даёт лучший компромисс ускорения и эффективности на 8-ядерных SoC.
- **ALL** имеет смысл подключать, когда модель вычислений изначально **MPI** (несколько узлов, разные адресные пространства); иначе накладные расходы и конкуренция за ядра могут съесть выигрыш.

## Вывод (с цифрами по таблицам выше)

**База SEQ.** Для входа 20 млн `int` в режиме `task_run` время последовательной реализации лежит в диапазоне **примерно 0,32–0,35 с**; в формулах ниже оно выступает как **`T_seq`** (точка отсчёта `S = 1`, **Eff = 100%**).

**OMP, TBB, STL при сравнении с SEQ.** По приведённым ориентировочным замерам на Apple M2 (Release):

- при **N = 2** ускорение **`S`** относительно SEQ составляет **1,86–1,91**; эффективность **`Eff = S/N`** — около **93–95,5%**. Лучшее **S** в этой тройке у **TBB (1,91)**; у OpenMP **1,88**, у STL **1,86**.
- при **N = 4** **`S`** вырастает до **2,55–2,64**; **`Eff`** снижается до **63,8–66%**. Снова максимум у **TBB (S = 2,64, Eff ≈ 66%)**; OpenMP **2,58 / 64,5%**, STL **2,55 / 63,8%**.
- при **N = 8** **`S`** достигает **2,92–3,05**, а **`Eff`** падает примерно до **36,5–38,1%**. Наибольшее ускорение у **TBB (3,05)**; OpenMP **2,98**, STL **2,92**.

Итого по потоковым веткам без MPI: **все три технологии дают монотонный рост `S` при увеличении N с 2 до 8**, но **эффективность падает** с ~94% до ~37% из‑за памяти, синхронизации и уменьшения параллелизма на верхних уровнях merge. На этих числах **TBB стабильно на 0,03–0,13 по `S` впереди** OMP и STL при каждом N из таблицы.

**ALL относительно SEQ (таблица «ALL» в этом файле).** При **`P = 1`**:

- при **N = 2**: **`S ≈ 1,87`**, **`Eff ≈ 93,5%`**;
- при **N = 4**: **`S ≈ 2,22`**, **`Eff ≈ 55,5%`**;
- при **N = 8**: **`S ≈ 2,93`**, **`Eff ≈ 36,6%`**.

То есть по отношению к SEQ версия ALL при одном ранге укладывается **между STL и TBB** по порядку величины: при **N = 8** **`S ≈ 2,93`** для ALL **ниже**, чем у TBB (**3,05**) и OpenMP (**2,98**), но **выше**, чем у STL (**2,92**) — что согласуется с ожидаемыми накладными расходами MPI при **`P = 1`**.

При **`P = 4`** на одном узле в той же таблице **`S ≈ 2,31`** при **N = 2** и **`S ≈ 2,16`** при **N = 4**; общеузловая эффективность **`S/(PN)`** получается **≈ 28,9%** и **≈ 13,5%** соответственно, то есть добавление процессов без выделенных ресурсов **сильно снижает** отдачу на «параллельную единицу» **`P·N`**.

**Дополнение по масштабированию потоков у ALL (`P = 1`).** В файле **`all/report_performance.md`** приведена **медиана по нескольким прогонам** (разгруженная система), например: **`T_all(1) ≈ 0,313 с`**, **`T_all(2) ≈ 0,203 с`**, **`T_all(4) ≈ 0,140 с`**, **`T_all(8) ≈ 0,127 с`** при **`T_seq ≈ 0,325 с`**. Отсюда **`S_par = T_all(1)/T_all(N)`** даёт **≈ 1,54 → 2,24 → 2,46** для **N = 2, 4, 8**, а **`Eff_par = S_par/N`** — **≈ 77%**, **≈ 56%**, **≈ 30,8%**: при переходе с **4** на **8** потоков выигрыш по времени **умеренный** (~**10%** к медианному `T_all(4)`), что указывает на **насыщение** по памяти и по параллелизму merge.

**Итоговая формулировка.** На тестовом входе **20 млн** элементов все параллельные реализации **ускоряют** работу относительно SEQ в терминах табличных **`S`**; среди чистых потоковых реализаций по этим ориентирам **лидирует TBB** (максимальные **`S`** при **N = 2, 4, 8**). **ALL** при **`P = 1`** остаётся конкурентоспособным к STL/OMP, но **уступает** лучшим потоковым временам при больших **N**; при **`P > 1`** на одном узле **падает** **`Eff_global`**, поэтому для отчёта по распределённым запускам нужны **отдельные** замеры на целевой конфигурации **`mpirun`**.
