## Введение

Последовательная реализация задаёт **эталон корректности** и **базовое время** `T_seq` для сравнения с многопоточными вариантами (OpenMP, TBB, STL) и гибридом MPI+потоки (`all`). В отличие от параллельных веток, здесь нет гонок за данными и накладных расходов планировщика: поведение проще анализировать и отлаживать.

Общая идея задачи: **LSD radix sort** по 32-битным `int` с учётом знака плюс **устойчивое слияние** двух уже отсортированных половин. Подробности общей постановки и констант см. также в `common/include/common.hpp` и в отчётах параллельных реализаций при необходимости сопоставления.

## Постановка задачи

На вход подаётся непустой массив целых чисел. На выходе требуется перестановка тех же элементов, упорядоченная по неубыванию.

Требования к SEQ-ветке:

- выполнение **в одном потоке**, без OpenMP/TBB/MPI;
- результат совпадает с эталоном (`std::sort`) на всех функциональных тестах;
- время `Run()` в режиме производительности используется как **`T_seq`** в формуле ускорения `S = T_seq / T_par` для остальных технологий.

## Связь с кодом и структура данных

- Файл: `seq/src/ops_seq.cpp`.
- Класс задачи: `SosninaATestTaskSEQ`.
- Основной контейнер: `std::vector<int>` для входа/выхода и для копий половин `left_part`, `right_part`.
- Для каждой половины выделяется отдельный буфер той же длины, что и соответствующая часть, для поразрядной фазы (двухбуферная схема).

## Описание алгоритма

### Декомпозиция

1. Если `data.size() <= 1`, сортировка не нужна.
2. Иначе `mid = data.size() / 2`: левая часть `[0, mid)`, правая `[mid, n)`.
3. Обе части копируются в новые векторы (исходный `data` не мутируется по месту до финального слияния в выходной буфер).

### RadixSortLSD (общая схема для `int`)

Константы в коде:

- `kRadixBits = 8`, основание `kRadixSize = 256`;
- число проходов `kNumPasses = sizeof(int) / sizeof(uint8_t)` (для 32-битного `int` — **4** прохода);
- для знаковых значений до и после проходов применяется XOR с `kSignFlip = 0x80000000U`, чтобы порядок ключей совпадал с обычным сравнением целых.

На каждом проходе LSD:

1. Подсчёт частот «цифр» (байт разряда) в массиве `count[0..256]` (в коде вектор длины `kRadixSize + 1` с префиксами).
2. Префиксные суммы для позиций записи в буфер.
3. Распределение элементов во второй буфер по текущему разряду.
4. Обмен ролей массива и буфера.

Сложность одного прохода по длине части `m`: **O(m)** времени и **O(256)** дополнительной памяти на массив счётчиков. Итого по части: **O(4 · m) = O(m)** при фиксированном числе разрядов.

### SimpleMerge

Два отсортированных вектора сливаются в третий линейным проходом с двумя указателями; при равенстве элементов сначала берётся элемент из левой части (**устойчивость** относительно исходного порядка в половинах).

### Псевдокод

```text
Вход: data
если |data| <= 1: конец
mid <- |data| / 2
left  <- копия data[0 .. mid)
right <- копия data[mid .. |data|)
LSD-sort(left,  буфер_left)
LSD-sort(right, буфер_right)
merge(left, right) -> data
проверка: is_sorted(data)
```

## Оценка сложности и памяти

Пусть `n = |data|`, `n1 = mid`, `n2 = n - mid`.

- **Время:** O(n) на radix по каждой половине плюс O(n) на слияние → **O(n)** при фиксированном числе бит на `int`.
- **Память:** две копии половин O(n), два буфера radix O(n1)+O(n2), итоговый буфер под результат слияния O(n) → **линейная** дополнительная память относительно `n`.

## Ограничения и замечания

- Две фиксированные половины дают **ровно одно** слияние после radix — проще, чем дерево из нескольких частей в параллельных версиях, но нет внутреннего параллелизма.
- Копирование половин увеличивает трафик памяти по сравнению с in-place стратегиями; для учебной задачи это приемлемый компромисс за простоту.
