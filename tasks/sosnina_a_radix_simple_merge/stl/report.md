## Введение

STL-ветка использует только стандарт C++: **`std::thread`**, **`std::vector`**, **`std::ranges::merge`**. Это даёт **переносимость** без линковки OpenMP и без зависимости от oneTBB, в обмен на ручное управление разбиением индексов и явный `join` всех потоков.

Локальная схема radix+merge **совпадает по идее** с локальной фазой в `all` (`SortLocalStlParallel` в `all/src/ops_all.cpp`), что упрощает сравнение гибрида MPI+потоки с «чистой» многопоточностью на одном ранге.

## Постановка задачи

Реализовать корректную многопоточную сортировку с тем же входом/выходом, что и остальные варианты, используя явный параллелизм потоков и те же числовые пороги зернистости, что и в TBB-версии (константы в одном стиле).

## Связь с кодом

- Файл: `stl/src/ops_stl.cpp`.
- Класс: `SosninaATestTaskSTL`.
- Вспомогательная функция: шаблон **`ParallelForRange(begin, end, num_threads, fn)`** — диапазон `[begin, end)` режется на не более `num_threads` кусков, для каждого куска создаётся `std::thread`, в конце выполняется `join`.

## Описание реализации

### ParallelForRange

- Если `begin >= end`, выход.
- Эффективное число потоков: `max(1, min(num_threads, end - begin))`, чтобы не создавать лишние потоки при малом числе итераций.
- Каждый поток обрабатывает непрерывный поддиапазон индексов `[lo, hi)` и для каждого `i` вызывает `fn(i)`.

Используется дважды: для индексов частей на фазе radix и для индексов пар на каждом уровне merge.

### Выбор num_parts

Логика совпадает с TBB-веткой по смыслу (см. `kMinElementsPerPart`, `kMinElementsPerPartSmall`, `kSmallArrayThreshold`, `kLargeArrayThreshold`, `per_thread_floor`, `min_chunk`, `max_parts_by_grain`, `num_parts = min(num_threads, n, max_parts_by_grain)`).

### Radix и merge

- `RadixSortLSD` — тот же 8-битный LSD, 4 прохода, XOR для знака; счётчики в `std::array<int, kRadixSize + 1>`.
- `SimpleMerge` — `std::ranges::merge` в заранее выделенный буфер результата.

### Псевдокод

```text
вычислить num_parts (пороги + GetNumThreads())
разбить data на parts

ParallelForRange(0, num_parts, num_threads):
    для i из своего диапазона:
        LSD-sort(parts[i])

current <- parts
пока |current| > 1:
    pair_count <- |current| / 2
    ParallelForRange(0, pair_count, num_threads):
        для idx из своего диапазона:
            next[idx] <- merge(current[2*idx], current[2*idx+1])
    хвост при нечётном |current|
    current <- next
data <- current[0]
```

## Отличия от OpenMP

- Нет директив компилятора: проще собирать в средах с «частичной» поддержкой OpenMP, но **больше кода** на ручное управление потоками.
- Пороги зернистости **согласованы** с TBB, в отличие от упрощённой формулы `num_parts` в OMP-файле.

## Оценка сложности

- **O(n)** по времени при фиксированной разрядности ключа.
- Дополнительные накладные расходы: создание/уничтожение `std::thread` на каждом вызове `ParallelForRange` (на уровне merge это происходит на каждом уровне дерева — для отчёта полезно упомянуть как фактор, влияющий на малых `n`).

## Экспериментальные результаты (ориентир)

Apple M2, macOS, Release, `task_run`, 20 млн элементов.

`S = T_seq / T_stl`, `Eff = S / N`.

| N потоков | Ускорение S | Эффективность Eff |
| --------- | ----------- | ----------------- |
| 2         | 1,86        | 93%               |
| 4         | 2,55        | 63,8%             |
| 8         | 2,92        | 36,5%             |

Результаты близки к OpenMP; небольшое отставание от TBB на тех же `N` согласуется с различиями планировщика и накладных расходов.

## Анализ

- На **N = 2…4** версия даёт стабильный выигрыш над SEQ и остаётся конкурентной относительно OMP.
- На **N = 8** эффективность падает (как и у других веток): память, мало параллельных пар на верхних уровнях merge, стоимость потоков.

## Вывод

STL-версия корректна, не требует OpenMP/TBB в рантайме и демонстрирует производительность, сопоставимую с OpenMP на рассматриваемой платформе, оставаясь удобной базой для сравнения с **ALL** на одном MPI-процессе.
